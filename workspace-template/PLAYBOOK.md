# Shared execution playbook

## Start and recover

Read your assigned role and POLICY.md. Leads read vault/Bridge.md,
vault/Board.md, vault/Implementation-queue.md and the active project note.
Workers read only their role, explicit brief, applicable repository instructions
and the source material the assignment needs. Repeat after compaction.

Verify live identities, checkouts and pending runs before resuming dependent
actions. A saved pane name or session ID is history, not current ownership.
Preserve active work and human input. An idle agent with a live CI watcher is
waiting, not necessarily stalled. Recover only a confirmed stall.

## Delivery

1. Define the observable outcome, scope, accepted decisions, authority and stop
   conditions in one self-contained brief. Name the exact project and report paths.
2. Check consequential assumptions at the source before building. Trace inputs,
   keys, units, aggregation and the actual consumer. Separate measured facts,
   inherited evidence and assumptions. Reuse valid evidence at pinned revisions.
3. Material changes to a served surface, schema, policy, source or grain receive
   a fresh independent plan review before dependent coding. Routine implementation
   details within an accepted design do not need another architecture ceremony.
4. A builder implements in a fresh dedicated Git worktree, runs appropriate
   existing checks, writes a report and stops at the brief's next boundary.
5. The implementation lead checks intent, scope and minimalism. It advances
   through authorized push and draft-PR steps without relaying routine approvals.
6. A fresh reviewer from the other model family reviews code and evidence with
   a self-contained brief, without the builder's conversation. The reviewer
   independently checks the critical claims and seeks simpler implementations.
7. Triage findings: fix, rebut with evidence, or defer explicitly. Keep the same
   builder through fixes. Re-review the meaningful increment, not unchanged work.
8. Merge/deploy only within explicit authority. Verify the actual delivered
   version and consumer. A successful build is not proof of refreshed data or a
   rendered UI. Identify external publication steps separately.
9. Close only the verified outcome. Record unfinished consumers, access limits
   and their concrete resume event. An inactive adapter is a milestone, not delivery.

## Evidence

- A comparison uses complete keys and compatible source versions. Count unmatched
  rows and duplicate-producing joins before trusting totals. Do not silently dedupe.
- A code delta is old versus new logic on the same inputs; a historical table
  delta can also contain source movement. Label which one you measured.
- Check a claimed blocker against the exact command and error. Missing permission,
  missing evidence, unfinished implementation and external dependency differ.
- Preserve null, zero, negatives, currency and time rules. A company vote is not
  proof of the units of every underlying transaction.
- Record what ran, failed, was skipped or remains unverified. Source-to-source
  agreement is not independent proof when both depend on the same wrong producer.

## Communication

Workers write the full report first, then send one brief completion or waiting
message to their immediate parent from the brief. Never guess another recipient.
The implementation lead sends the main agent only verified outcomes, material
scope changes, decisions it cannot own, or external blockers it cannot resolve.
Use at most three short sentences plus the report path. Do not forward routine
dispatches, CI waits or acknowledgments. Answer direct status questions plainly.

Normal worker events resume the workflow. Keep one watcher per external event;
do not run polling loops or repeated progress pings. A confirmed crash needs a
report/worktree/run reconciliation before restart, not a second parallel builder.

## Notes

The project note holds current state, decisions and next action. The queue holds
execution order and shared-resource ownership. Reports hold detailed evidence.
Replace stale current summaries instead of appending conflicting "current" blocks.
Keep old evidence clearly marked as history. GitHub issues must be self-contained
and use accessible GitHub links, not private vault paths.
